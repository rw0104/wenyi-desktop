# 0.6 任务规划

本文档记录 2026-09-13 排查发现的问题与后续排期。已完成项保留在文末，便于对照。

排序依据：**能造成数据或额度损失、或让用户误判任务状态的，优先于增加能力。**

---

## P0 · 本次排查发现（先修）

### P0-1 误触即报错：只有一本书时点击它，被当成"切换书籍"

**现象**（用户报告，07:58:06 与 08:04:10 两次）：

```
翻译进行中，暂时不能切换书籍。请先点「取消」，或等它结束。
```

书架上**只有一本书**，用户点击它——没有任何东西可切换，却被当成一次非法操作并弹出错误。

**位置**：`ui/shelf.js:165`

```js
function select(input) {
  if (window.__runningGuard && !window.__runningGuard()) return;
  selected = input;
  ...
}
```

`select()` 没有先判断"点的就是当前这本"，直接进了守卫。

**修法**：在守卫之前短路。

```js
function select(input) {
  // Re-selecting the current book is a no-op, not a forbidden switch. With a single book on
  // the shelf this was the only thing a click could do, so every click produced an error.
  if (input === selected) return;
  if (window.__runningGuard && !window.__runningGuard()) return;
  ...
}
```

**验收**：运行中点击已选中的书 / 唯一一本书 → 日志无新增错误行；点击另一本 → 仍然拒绝并给出提示。

### P0-2 `render()` 把守卫当钩子用，导致假错误日志

**位置**：`ui/shelf.js:157`

```js
if (window.__runningGuard) window.__runningGuard();   // 副作用是"写一条错误日志"
```

`window.__runningGuard`（`ui/main.js:136`）是个**守卫**：运行中返回 `false` 并写错误日志。
`render()` 调用它却完全无视返回值——纯粹为了副作用。于是**任何一次书架重渲染**在运行中都会往日志里塞一条"不能切换书籍"。

这解释了为什么用户看到的是**两条相隔 6 分钟**的消息：不是只有点击才会触发。

**修法**：`render()` 不需要这个调用，直接删除。若确实想在运行中做视觉状态同步，应改为调用一个真正的钩子（如 `window.__onShelfRendered`），而不是复用守卫。

**验收**：运行中触发任意一次书架刷新（添加、移除、设置变化）→ 日志无"不能切换书籍"。

---

### P0-3 `terminated` 不复位运行状态

**位置**：`ui/main.js:685`

```js
case "terminated":
  log(`引擎退出，退出码 ${payload.exitCode}`, "engine");
  break;
```

只写日志，不调用 `setRunning(false)`。目前靠 `startRun()` 里 `await call("run_engine", …)` 的
`finally` 兜底（`ui/main.js:610`）——引擎进程退出 → Rust 侧循环 break → 命令返回 → Promise 兑现 → 复位。

但这条链有前提：**Rust 侧必须收到 `CommandEvent::Terminated`**（`src-tauri/src/lib.rs:997`）。
sidecar 是 PyInstaller `--onefile`，直接子进程是 bootloader，真正干活的是它的子进程。
只要出现"bootloader 已退出而子进程仍持有 stdout 管道"的情形，这条链就断了，UI 会**永远停在运行中**：
「开始 / 继续翻译」灰着、点书报错、只有「取消」能解开——**这正是用户描述的"必须点取消再点继续"**。

**修法**（两层，都要）：

1. `terminated` 事件本身就复位：`setRunning(false)` + `stopChapterPoll()`，不再依赖 Promise 链。
2. 加看门狗：Rust 侧在 `run_engine` 返回后（无论走哪条分支）都补发一个终态事件；
   前端再按"最后一次事件距今 N 秒且 `state.running` 仍为真"做兜底复位。

**验收**：手动 `taskkill` 掉引擎进程 → UI 在数秒内回到空闲态，可直接点「继续翻译」，无需先点「取消」。

### P0-4 待确认：用户报告"任务停止"

**用户描述**：误触之后"他就停止任务，需要手动点取消再点继续"。

**当前证据不支持"引擎真的停了"**。事件日志按分钟统计（07:57–08:04）：

| 时刻 | 请求开始 | 完成 | 失败/重试 |
|---|---|---|---|
| 07:58 | 3 | 3 | 0 |
| 07:59 | 4 | 4 | 0 |
| 08:00 | 3 | 3 | 0 |
| 08:01 | 3 | 3 | 0 |
| 08:02 | 2 | 2 | 0 |
| 08:03 | 4 | 4 | 0 |
| 08:04 | 3 | 3 | 0（另有 37 条为重启后的启动事件） |

引擎在这 7 分钟里**持续出活、零失败、无空档**；新的引擎进程启动于 08:04:23，即用户取消并继续之后。
进程列表里也没有孤儿（0.5.5 的进程树终止生效）。

**结论**：更像 P0-3 所述的"UI 卡在运行态"，而不是引擎真的停止——用户看到红色报错、日志随后安静下来，
自然会判断成"任务被停了"。

**待用户确认**：误触之后，进度条是否还在走？日志是否还有新的 "开始翻译：xxx"？
若两者都停了而引擎仍在写 `events.jsonl`，则是前端事件订阅断链，属于另一类缺陷。

## P1 · 用户指定顺序

### P1-1 术语表可见（#2）

**问题**：引擎有完整的术语表能力，界面**完全没有入口**。翻译工具看不到术语表，
用户无法发现和纠正"同一个人名三种译法"这类问题。

**引擎侧能力**（已核对）：

| 子命令 | 作用 |
|---|---|
| `glossary list` | 列出已确立的术语译法与状态 |
| `glossary conflicts` | 列出**未解决**的译法冲突 |
| `glossary resolve` | 把一个术语定到指定译法并关闭其冲突 |

**关键约束（已实测）**：翻译进行中，CLI 会失败——

```
$ wenyi-core.exe -c config.yaml glossary list <book>
Error: [Errno 36] Resource deadlock avoided
```

`status` 同样如此。**但直接以只读方式打开 SQLite 是可以的**（WAL 模式）：

```
只读打开: 成功     glossary 3412 行    term_conflicts 116 行
```

**方案**：不做 CLI 转发，改为**从 Rust 侧只读打开 `glossary.db`**。
- 新增依赖 `rusqlite`（`bundled` 特性，避免要求用户装 SQLite）。
- 用 `mode=ro` 打开，运行中也能读，实时刷新。
- `glossary` 表列出术语；`term_conflicts` 表（本机当前 **116 条未解决**）单独一栏，这是最有价值的部分。

**界面**：翻译页新增一张卡片「4 · 术语表」，或作为续跑页的第二个面板。
按 §16（分组与映射），术语属于"这本书"的属性，应与书放在一起。
只读优先——`glossary resolve` 会写库，必须等运行结束，第一版先不做写操作，避免与引擎抢锁。

**验收**：任意一本书翻译过程中打开术语表 → 显示术语与冲突条数；不阻塞翻译；文件锁冲突时给出可读提示而不是崩溃。

### P1-2 清除状态重新开始（#3）

**问题**：`remove_book` 只从书架列表移除——`src-tauri/src/library.rs:67` 仅重写 `library.json`，
`state/` 目录原封不动。用户跑砸了想从头再来，**没有任何入口**，只能手动删 `%APPDATA%\com.wenyi.desktop\workspace\state\`。

**修法**：
- 新增命令 `forget_book(input)`：按文件摘要定位 state 目录并删除，同时从书架与历史移除。
- 明确区分两个动作，且**不要**合并成一个：
  - 「从书架移除」——可逆，不动文件、不动状态（已有）
  - 「清除翻译状态」——**不可逆**，删除 state，需要确认对话框
- 依据 §16「确认框只用于真正破坏性且不可逆的操作」，这里是它该出现的地方；§2 同时要求
  「宽容」——所以按钮文案要写清楚会失去什么（已完成 N 章会被丢弃）。

**验收**：清除后同一文件重新开始 → 从 0 开始，不出现"已从 N/M 继续"；书架与续跑列表都不再出现该书；
误点时有确认且可取消。

### P1-3 审校只读模式（#5）

**问题**：`pipeline.review_autofix` 默认 `true`，审校会**直接改写正文**。
用户无法选择"只给建议、我自己判断"。这个选项有实际后果却没有任何界面。

**修法**：
- 设置页「质量」区域新增开关：**「审校自动改写正文」**，默认保持引擎默认（开），
  关闭时传 `--no-autofix`（`review` 子命令支持该旗标，`pipeline.review_autofix` 同样可配）。
- 关闭时，审校结果应当**有地方可看**，否则等于没有产出。最小实现：
  把引擎生成的审校报告（`report.json` 中的审校段落）在界面上列出。
  这是本条能成立的前提——只关掉改写而不给结果，用户什么也没得到。
- 与 P1-1 共享一个面板：「审校建议」与「术语表」都属于"引擎发现了什么"。

**验收**：关闭自动改写后跑一本书 → 正文保持原样，建议在界面上可见且能定位到章节。

## P2 · 待排期

### P2-1 多书队列与并发

用户指出"多书翻译也应该是并发任务"。当前 `run_engine` 用
`SidecarState(Mutex<Option<CommandChild>>)`（`src-tauri/src/lib.rs:32`）只持有一个子进程，
并在入口直接拒绝第二次启动（`src-tauri/src/lib.rs:887` 附近）。

**可行性分析（已核对引擎）**：
- 每本书的 state 目录互相独立（`state/<book>/targets/<lang>/`），术语库也是每本一个 → **跨书并发在状态上是安全的**。
- 引擎**单本内部**的正文翻译是串行的，这是设计使然（滚动上下文 + 增量术语表用于保持全书一致），不要试图并行化单本。
- **必须一并解决的共享资源**：
  1. `config.yaml` 只有一份，`run_engine` 每次启动都重写它（`settings::write_engine_config`）。
     两个并发运行会用同一份配置——**必须改成每次运行写单独配置文件**。
  2. `history.json` / `library.json` 的读写需要加锁，避免并发覆盖。
  3. 供应商限流是共享的：N 本书并发并不提升总吞吐，只是把同一份配额切碎。
     默认应当是**串行队列**，并发作为可选项并说明其代价。

**建议**：先做**队列**（加入待办 → 依次执行 → 可调整顺序），并发留到队列稳定之后。

**验收**：一次选中三本书 → 排队依次翻译；中途取消当前这本不影响队列其余；应用重启后队列可恢复。

---

### P2-2 设置页信息层次重做

按 apple-design §6 / §16 审查现有设置页：

- 所有字段同等重量排成一列：提供方、模型 ID、base_url、**「密钥环境变量名（可选，高级用法）」**、自定义密钥、代理、批量长度。
- 最该被看见的是**「实际请求」**这一行（真实端点 + 真实模型），却埋在第四个字段下面、以小字呈现。
- 「存储位置」三行长路径与主要设置同级展示，属于诊断信息。

**修法**：常用项直接展示；高级项收进「高级」折叠区（`<details>` 即可，无需新组件）；
把「实际请求」提到卡片顶部作为该卡片的结论行。§6：「常见路径先给，高级选项降一级」。

### P2-3 续跑页与书架合并

两处都列书 + 进度，且**数据源不同**（书架读 `library.json`，续跑读 `history.json`），可以互相不一致。
书架显示「已完成 11/21 章」，续跑页显示同一本书的另一套计数。

**修法**：一个列表，两种排序/筛选（在翻译中 / 已完成 / 全部）。§16「看起来一样的东西应当住在同一个地方」。
